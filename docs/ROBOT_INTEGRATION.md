# Adding BALTA Crucible to an existing robot project

The robot side is a small Java library (`robot-lib/`, package `lib/simbridge` plus `lib/TalonFXSim.java`) and a few lines in your code. It is simulation only: it does nothing unless the environment variable `CRUCIBLE_BRIDGE=1` is set, which the app does when it launches the robot, so it is safe to leave in the project and it never runs on the real robot.

Works with: Java, WPILib 2026, CTRE Phoenix 6 swerve generated by Tuner X (`TunerConstants`, a drivetrain class extending `TunerSwerveDrivetrain`), Talon FX mechanisms.

## One command

From the Crucible `app` folder:

```
node scripts/integrate-robot.mjs "C:\path\to\your\robot-project"           (check: shows what is there, changes nothing)
node scripts/integrate-robot.mjs "C:\path\to\your\robot-project" --apply   (installs)
```

`--apply` does these four things (each one is skipped if it is already done, so it is safe to run twice):

1. Copies the library into `src/main/java/<your package>/lib/` (the package name is read from `Robot.java`, or pass `--package`).
2. Adds this block next to the `drivetrain.registerTelemetry(...)` line (where the drivetrain is in scope; `TunerConstants` is imported if needed):
   ```java
   // BALTA Crucible: hand the drivetrain physics to the simulator app (simulation only; does nothing unless CRUCIBLE_BRIDGE=1)
   if (RobotBase.isSimulation() && SimBridge.isEnabled()) {
     SimBridge.installSwerve(drivetrain, TunerConstants.FrontLeft, TunerConstants.FrontRight, TunerConstants.BackLeft, TunerConstants.BackRight);
   }
   ```
3. In your drivetrain class, changes `if (Utils.isSimulation()) { startSimThread(); }` to `if (Utils.isSimulation() && !SimBridge.isEnabled()) { ... }`. Without this CTRE's own drivetrain simulation would move the wheels a second time.
4. In `build.gradle`, changes `wpi.sim.addGui().defaultEnabled = true` to `!"1".equals(System.getenv("CRUCIBLE_BRIDGE"))`. Without this the simulation GUI overwrites the app's joystick and Driver Station data every frame and the robot never moves.

Then build once (`gradlew build`), start BALTA Crucible, open the **Robot** tab, pick **Robot code (real time)** and press **Launch robot**. `--remove` takes the block and the sim-thread guard out again (it leaves the copied library files and the `build.gradle` line; delete or revert those by hand).

Checked by applying it to the OffSeason robot project as it was before the bridge existed: it compiled and, started from the app, drove over a BUMP and into a wall with odometry that follows the physics.

## Mechanisms (turret, hood, shooter, intake, ...)

The swerve modules are handled above. Every other Talon FX needs its physics from the app instead of a `DCMotorSim`. If you already simulate a mechanism with a physics object that sets the Talon's rotor position and velocity (the usual `TalonFXSimState` pattern), replace that with `TalonFXSim`, which does the same and, when the bridge is on, registers the motor with the app:

```java
// TalonFXSim(motor, DCMotor model (with the number of motors that share the load), sensorToMechanism ratio, inertia kg*m^2, inverted)
sim = new TalonFXSim(turretMotor, DCMotor.getKrakenX60(1), TurretConstants.GEAR_RATIO, 0.1, false);
if you re-zero the motor in code (setPosition(0)), also call: sim.resetPosition();
```

The app needs to know the same mechanism (CAN id, motor, gear ratio, inertia) in its robot definition `robots/<name>/robot.yaml`; when the robot connects, the app compares that file with what the code registered and lists any difference. At the moment the app ships one robot definition (OffSeason); a second robot needs its own `robot.yaml` and an entry in `src/robots/` (see the OffSeason one for the fields).

A Talon FX with no physics registered keeps running on the Phoenix simulation with no load, as before.

## Lockstep (Mode B, optional)

Mode B (deterministic, faster than real time) replaces the Talon firmware control loops with `EmuTalon` and CTRE's swerve control with `EmuSwerve`, so the robot code must be able to use them. It is more work and needs your IO layer:

- Mechanisms: an emulated IO next to each real/sim IO, built from the same config object and registered with `SimBridge.registerEmu(...)`; see `robot-lib/examples/EmuIOs.java.txt` for all seven OffSeason mechanisms, and select it with `SimBridge.isLockstep()` where the IO is chosen.
- Swerve: the drivetrain class delegates `setControl`, `registerTelemetry`, `resetPose`, `addVisionMeasurement`, `samplePoseAt`, `setOperatorPerspectiveForward` and the yaw rate to an `EmuSwerve`, and code reads the state through your own `state()` (CTRE's `getState()` is final); then `Robot()` calls `SimBridge.installLockstep(drivetrain.emuSwerve())`. The OffSeason `CommandSwerveDrivetrain` shows every change.
- `Robot.simulationInit()` calls `SimBridge.markRobotStarted()` and `robotPeriodic()` calls `SimBridge.markLoopIteration()` when `SimBridge.isLockstep()`.
- Vision (PhotonVision sim) must be off in lockstep, because its random noise and NetworkTables timing are not repeatable.

Mode A (real time) is enough for driver practice, tuning and most testing; add Mode B when you want repeatable batch runs.

## Vision (optional, not read yet)

The app sends the robot a message about every 50 ms of simulated time (bridge type 9, see NT_CONTRACT section 15): with the vision camera switched on (Robot tab) the AprilTags the simulated camera sees and a noisy robot pose, with it off the exact pose. The robot library reads it and calls `addVisionMeasurement` on the drivetrain's pose estimator (`EmuSwerve.visionPose` in lockstep), so odometry that keeps counting while the robot is held by a wall cannot run away from the physics.

## If something does not work

- **The robot connects but does not move:** the simulation GUI is still on (step 4), or CTRE's drivetrain sim is still running (step 3).
- **No connection:** another Crucible window is holding port 5811 (the robot accepts one app at a time), or the robot was not started by the app (it needs `CRUCIBLE_BRIDGE=1`).
- **The app lists differences after connecting:** the robot definition does not match the code (a different gear ratio, motor count or CAN id).
- **Keeping the library current:** the library is developed in the OffSeason project and copied into `robot-lib/` with `node scripts/sync-robot-lib.mjs`; a test fails if the copy is out of date.
